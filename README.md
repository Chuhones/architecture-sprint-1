## Задание 1

Поставлена задача разбить существующий монолитный фронтенд на микрофронтенды. 

# Выбор инструментов

В качестве фреймворка для создания микрофронтендов выберем 'Webpack Module Federation'. Он относительно простой в понимании процесса компоновки отдельных МФ и их взаимодействия. В то же время не требует привязки к одностраничному исполнению проекта, в отличие от 'Single SPA'. Это отчасти может дать больше возможностей маневра для расширения проекта небольшой командой без богатого опыта использования микрофронтендов.

# Планирование изменений

Выделим бизнес функции приложения:
 - Основная функция - **работа с альбомом**. Добавление, удаление, управление лайками.
 - **Авторизация** - возможность зарегистрироваться и авторизоваться
 - **Профиль пользователя** - отображение карточки пользователя и возможность ее изменить

В соответствии с этим выделим микрофронтенды
 - **mfe-album** - добавление и удаление фотографий, управление лайками
 - **mfe-auth** - авторизация и регистрация
 - **mfe-profile** - работа с профилем пользователя
 - **mfe-base** - базовый микрофронтенд, который задает окружение и основу для композиции остальных микрофронтендов
 - **microfrontend-lib** - библиотека, которая предназначена для выделения общих компонентов и их переиспользования в остальных микрофронтендах

Каждый микрофронтенд может быть вынесен в отдельный репозиторий SCM и разрабатываться независимо. **microfrontend-lib** вероятно должен на стадии сборки импортироваться в остальные МФ.


# Запуск проекта

Полноценный запуск проекта не прорабатывался в силу практически полного отсутствия опыта в js и фронтенде в целом. 

## Задание 2

Требуется предложить вариант разделения монолитной системы на микросервисы. 

# Решение

Решение описано в приложенном файле Task_2.drawio

Монолит представляет собой систему с фронтовой частью в виде Портала электронной площадки и бэкендом в виде Системы управления торговыми площадками. У системы есть взаимодействие с внешними платежными системами.

По данной задаче предполагается переработка именно бэкенда, как следствие Портал оставляем в прежнем виде, лишь добавив ряд неучтенных функций - работу с Апелляциями и Заявками на Техподдержку. 

Между фронтом и бэком предлагается ввести API шлюз. Он с одной стороны добавит слой информационной безопасности (на этом этапе в частности можно организовать проверку аутентификации), слой маршрутизации для возможности будущего масштабирования и слой абстракции для защиты данных. Также шлюзы имеет смысл внедрить между внешними сервисами и Системой, а также в слое взаимодействия с Администраторами и Сотрудниками поддержки.

Сам монолит предлагается разделить на следующие микросервисы:
 - **Система управления пользователями** - отвечает за регистрацию новых пользователей, управления профилем и функции авторизации.
 - **Система управления товарами и услугами** - каталог товаров и услуг, а также "Корзина" пользователя.
 - **Система управления аукционами** - отвечает за все процессы, связанные с проведением акуционов
 - **Система управления заказами** - отвечает за управление жизненным циклом заказа вплоть до оформления платежа
 - **Система управления платежами** - биллинговая система для проведения платежей черехз внешние платежные сервисы
 - **Система управления апелляциями** - отвечает за создание и обработку апелляций
 - **Система управления заявками на техподдержку** - отвечает за создание и обработку заявок на техподдержку
 - **Сервис сбора статистики** - получает уведомления о всех важных событиях в системе и генерирует отчеты по этим событиям
 - **Сервис уведомлений** - служит для организации отправки уведомлений пользователям различными каналами и по поводу различных событий

 Стек технологий и решений сохранен существующий. В качестве возможного пути развития стоит также рассмотреть внедрение брокеров сообщений для организации асинхронного взаимодействия (например при передаче уведомлений о событиях).
